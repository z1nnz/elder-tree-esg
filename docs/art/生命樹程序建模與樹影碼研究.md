# 生命樹程序建模與樹影碼研究

日期：2026-09-02

適用範圍：樹伴生命樹庭園的候選美術管線與分享／展演互動。

不在範圍：任務見證、優惠核銷、支付、登入或任何高價值安全驗證。

## 結論先行

1. `ez-tree` 值得採用為**離線的枝幹候選產生器**，用來快速探索主幹扭轉、不對稱枝條與剪影；不應嵌入樹伴 Flutter 或 Unity 的執行期，也不應直接把它的預設樹當正式生命樹。
2. 「樹旋轉到一個角度，投影成可掃描的 QR Code」值得做成**樹影碼**：生命樹的分享／展演彩蛋。它會很有記憶點，也適合讓一個樹伴圈把自己的歷程分享給別人。
3. 樹影碼不可以承諾「任意角度都能掃」。它只能在唯一的識別視角，呈現一個符合 QR 規格的平面投影；掃描失敗時必須立即提供同一內容的普通平面 QR Code。
4. 樹影碼不得取代合作店家的短效現場碼、行動見證或核銷流程。分享碼與交易／見證碼必須分開，否則視覺彩蛋會被錯當成安全憑證。

## 一、程序樹工具：`ez-tree` 的適用性

### 已查核的來源與版本

- 原始碼：[Daniel Greenheck 的 `ez-tree`](https://github.com/dgreenheck/ez-tree)，本次查核固定在提交 [`dcf309bd86bd521083d9c70f01f2de45fdc7c457`](https://github.com/dgreenheck/ez-tree/tree/dcf309bd86bd521083d9c70f01f2de45fdc7c457)。
- 套件資訊是 `@dgreenheck/ez-tree` `1.1.0`，以 Three.js 為同儕依賴；這是網頁／Three.js 工具，不是 Unity 套件。[套件定義](https://github.com/dgreenheck/ez-tree/blob/dcf309bd86bd521083d9c70f01f2de45fdc7c457/package.json)
- 作者的說明指出，網頁工具可輸出 PNG 與 GLB，並可用種子、主幹、分枝層級、外力、扭曲、錐度、葉量等參數產生樹。[工具說明與參數](https://github.com/dgreenheck/ez-tree/blob/dcf309bd86bd521083d9c70f01f2de45fdc7c457/README.md)
- 它可產生多層細節模型：預設遠距層約為完整三角面的 40% 與 20%，而且每層從同一骨架網格建立，能維持大致剪影。作者也特別提醒，直接把多層細節物件輸出為單一 GLB 會帶入所有層級。[層級細節說明](https://github.com/dgreenheck/ez-tree/blob/dcf309bd86bd521083d9c70f01f2de45fdc7c457/README.md)
- 授權為 MIT；若直接複製、修改或散布其程式碼或實質部分，必須保留原作者 Daniel Greenheck 的著作權與 MIT 授權文字。[原始授權](https://github.com/dgreenheck/ez-tree/blob/dcf309bd86bd521083d9c70f01f2de45fdc7c457/LICENSE)

### 對樹伴的判斷

| 面向 | 判斷 | 採用方式 |
| --- | --- | --- |
| 不對稱樹幹與分枝探索 | 適合 | 用固定種子產生三到五個枝幹候選，挑一個做人工雕整，不直接上線。 |
| GLB 交換 | 適合但不是終點 | 將候選 GLB 匯入 Blender，整理根部、主枝、掛點、法線與材質，再由既有 Blender 腳本輸出目前的 FBX／GLB。 |
| Unity 手機執行期 | 不適合直接採用 | 不把 JavaScript／Three.js 或即時程序生成器放入手機 App；目前 Unity 只載入審核過、可量測的資產。 |
| LOD | 可作參考，不能直接交付 | 以作者的多層細節概念產生候選後，拆成 Unity `LODGroup` 所需的獨立層級，逐層量測材質、透明葉簇與記憶體。不可把所有層級塞在同一個 GLB。 |
| 葉片、樹皮與紋理 | 不可直接假定可用 | MIT 程式授權不自動完成每張內建貼圖、匯出物或視覺資產的上線權利判定。正式候選只用樹伴自製／已登記材質，另做來源與授權檢查。 |

### 建議的候選資產管線

```text
ez-tree 固定種子候選
  → 匯出 GLB（只保留單一完整細節層）
  → Blender：人工調整剪影、根部、主枝與十二個掛點
  → 套用樹伴自製樹皮／葉簇，移除第三方紋理
  → Blender 輸出 FBX／GLB 與統計
  → Unity：材料、風動、降低動態、相機與 Android／iOS 實測
```

採用門檻不是「工具能匯出」。候選模型必須同時通過：

1. 比現有候選更有不對稱主枝與可辨識的正面剪影；
2. 保留十二個穩定紀念掛點，且不破壞既有資料識別；
3. 只使用登記過來源的材質；
4. 分層細節、透明葉簇與三角面數有可重現的統計；
5. Unity 的降低動態、畫面與中階手機效能均重新驗收。

## 二、樹影碼：從生命樹投影出可掃描 QR Code

### QR Code 的不可違反條件

QR Code 不是「看起來像馬賽克」就能掃。最新版 [ISO/IEC 18004:2024](https://www.iso.org/standard/83389.html)明定 QR Code 的符號特性、尺寸、錯誤更正、參考解碼與產製品質要求。DENSO WAVE 的官方資料說明，標準 QR Code 有版本 1 至 40，從 21 × 21 到 177 × 177 個模組，每升一版每邊增加四個模組。[版本與模組](https://www.qrcode.com/en/about/version.html)

四周必須保留完整、無任何枝葉、光點、邊框或文字的四模組安靜區；這不是裝飾，而是掃描器判定碼區的必要空白。[DENSO WAVE 的安靜區規則](https://www.qrcode.com/en/howto/code.html)  錯誤更正等級 L／M／Q／H 約可處理全部碼字的 7%／15%／25%／30%，但提高等級也會增加符號尺寸；它不是允許任意破壞定位圖案、計時圖案、格式資訊或安靜區的額度。[DENSO WAVE 的錯誤更正說明](https://www.qrcode.com/en/about/error_correction.html)

GS1 的一手實作指南也警告，模組格網一旦扭曲、改成非完整方格，或被圖片／標誌影響到定位圖案，就可能無法讀取；對比、反光、格網均勻性與固定圖案損壞都應納入驗證。[GS1 二維條碼實作指南](https://ref.gs1.org/guidelines/2d-in-retail/)  Android 掃描端可用 Google ML Kit 做驗收；官方要求每個有意義單位至少約 2 × 2 像素，並提醒失焦會降低辨識，串流結果也應以連續影格同值確認。[Google ML Kit 條碼掃描說明](https://developers.google.com/ml-kit/vision/barcode-scanning/android)

### 可做的技術方案

樹影碼不是讓自由生長的枝條「剛好」湊成 QR Code。那樣會因鏡頭距離、透視、樹的深度遮擋、微風、粒子與手機自動對焦而改變模組邊界。

正確的第一版做法是讓生命樹與一層**碼格葉簇層**共存。這段從正面樹景轉為正上方碼面的互動命名為「樹冠展證」：

1. 從伺服器取得短效、不可猜測的分享識別碼，只編碼短網址加不透明識別碼；不把圈名、成員姓名、位置、任務內容或長期授權憑證塞進 QR Code。
2. 產生版本 3 或 4、H 級的 QR Code。連同四格安靜區，分別是 37 × 37 或 41 × 41 格；這是原型的刻意保守選擇，實際版本仍依 token 長度重新計算。
3. 每個深色模組是一個固定、無半透明、無反光的立體方格，所有格面在「識別視角」投影到同一平面。三個定位圖案、校正／計時圖案與四周安靜區都不允許被葉片或特效碰觸。
4. 使用者點擊生命樹或「查看樹證」後，不旋轉樹本身；相機以約兩秒沿樹幹上升並有限環繞，從正面移至正上方。前段保持自然樹冠，接近識別角度的最後幾度才讓同位置碼格葉簇精準對齊，避免正面看起來像條碼牆。
5. 進入唯一的識別視角後，鏡頭鎖為正交投影或經校正的固定透視投影，停止景深、風動、粒子、瀑布與相機漂移，並切換成均勻高對比光線，呈現完整方形碼面。降低動態模式不播放環繞，直接淡入俯視碼面。
6. 若掃描器在短時間內沒有讀到，就以約 0.2 秒轉場顯示同一 token 的普通平面 QR Code；功能成功不依賴觀眾是否能從三維視覺特效讀碼。

這仍然是「一棵樹變成 QR Code」：樹不動，觀看視角從正面繞到樹頂；立體模型在正常視角保有生命樹的形狀，在唯一俯視角給出一張真正規格化、能被第二台手機讀取的碼面。

樹冠展證可以共用相同動畫外殼，但編碼用途必須分流：真實植樹履歷使用可長期公開的短網址；圈子故事使用經同意的分享網址；會員識別若具有權限或福利，必須使用短效動態識別碼並由伺服器驗證，不可把長期會員權限直接寫進可截圖轉傳的固定碼。

### 原型門檻與驗收矩陣

以下是工程保守門檻，不是 ISO、DENSO WAVE、GS1 或 Google 所保證的通用成功率：

| 項目 | 第一版門檻 | 理由 |
| --- | --- | --- |
| 編碼內容 | 短網址＋一次性、不透明識別碼 | 控制版本大小，避免外洩個資與長期憑證。 |
| QR 版本 | 優先 3 或 4 | 分別為 29 × 29、33 × 33 模組，能在手機分享畫面維持較大的單格。 |
| 錯誤更正 | H 級 | 對螢幕反光或少量遮蔽保留容錯，但不作為修改功能圖案的理由。 |
| 螢幕單格 | 識別視角至少 8～10 螢幕像素 | 高於 ML Kit 約 2 像素的最低辨識條件，留給螢幕截圖、對焦與不同鏡頭的誤差。 |
| 安靜區 | 四邊完整 4 格 | QR 規格條件，不設計成草地、邊框或發光。 |
| 動態 | 展碼時完全靜止 | 避免動態模糊、投影漂移與格面穿插。 |
| 成功判定 | 每種情境連續讀到同一 token 至少 3 次 | 避免把偶然辨識當作可展示功能。 |

實機測試最少分 Android 與 iOS 各一台，並測試：直拍、左右／上下各約 15° 與 30°、近中遠距離、日光／室內／低光、正常動畫切入與靜止展碼。Android 可再用 ML Kit 的串流掃描作開發驗收；最終仍要加入使用者手機原生相機測試。任一組常態失敗時，該情境只能顯示平面 QR Code，不能宣稱「可掃」。

### 明確不承諾的事情

- 不承諾任意視角、距離、光線、螢幕亮度、手機機型或動畫途中都能掃到。
- 不承諾選 H 級後就能任意刪去或改畫約 30% 的 QR 圖樣。
- 不把立體投影碼用作進店核銷、任務完成、付款、登入、志工時數或真實影響紀錄；需要權限的會員識別只把短效識別內容裝進同一展示外殼，安全性仍由伺服器驗證，且永遠提供標準平面碼退路。
- 不用分享識別碼回傳精確位置、成員清單或未經同意的歷程資料。

## 三、雙樹架構：共行生命樹與真樹典藏

生命樹不再用同一個模型同時承擔「每日養成」與「真實植樹證明」。兩者的美術目的、更新頻率與可信度不同，正式拆成互相銜接的兩套體驗：

| 體驗 | 角色 | 美術與功能 |
| --- | --- | --- |
| 共行生命樹 | 樹伴圈每天共同養成的遊戲主樹 | 風格化、親切、手機友善；以穩定掛點更換季節枝、紀念葉、相聚果實與圈子收藏；可承載樹影碼分享彩蛋。 |
| 真樹典藏 | 實際植樹完成後取得的長期收藏 | 依合作單位回報的真實樹種建立較精緻的三維樹種模型，並連結種植日期、區域、照片、合作單位與可核驗紀錄。多年後形成圈子的真樹圖鑑。 |

「揭曉樹種」可以保留盲盒般的期待感，但不可設計成抽獎或由稀有度決定實際種植。真實樹種必須由合格合作單位依土地、氣候、原生性與生態需求先行決定；玩家完成旅程後揭曉的是適地樹種與其故事。若只能證明樹種與種植批次，介面就不得宣稱三維模型是某一棵個體樹的精確數位分身。

建議的完整循環為：

```text
共行生命樹累積已見證行動
  → 達成真實植樹進度
  → 合作單位依場域完成適地植樹並回傳證據
  → 揭曉真樹典藏與樹種故事
  → 樹影碼分享公開故事／植樹憑證
  → 開始下一棵共行生命樹旅程
```

## 四、建議的下一個獨立原型

建立一個不接真實帳號、不接任務、不接核銷的「樹影碼展示樣本」：固定使用測試 token，做出一棵簡化生命樹、一層正交投影可讀的立體碼格層，以及平面 QR Code 退路。驗收只回答三件事：

1. 正常視角時，它是不是仍像樹伴的生命樹，而非一面條碼牆？
2. 識別視角時，兩種手機能不能重複掃到相同測試 token？
3. 失敗時，使用者能不能不費力地用平面碼完成同一件事？

三項都通過後，才把它接到「分享我的生命樹」；仍不可直接接到任何有價值回饋或見證流程。
